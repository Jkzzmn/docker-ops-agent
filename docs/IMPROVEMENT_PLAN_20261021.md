# Docker Ops Agent 신뢰성 개선 개발 기획안

작성일: 2026-10-21 · 기준 버전: API 2.4.0 · 상태: **구현 전 기획안**

## 1. 목표와 근거

목표는 에이전트 수를 늘리는 것이 아니라 **사용자가 요청한 대상을 실제로 확인하고, 근거로 입증할 수 있는 내용만 설명하는 서비스**로 만드는 것입니다. 기존 FastAPI·LangGraph·MCP·Vue·SQLite·Ollama 구조를 유지합니다.

근거는 [비판적 평가 보고서](CRITICAL_REVIEW_20261021.md)와 실제 Ollama 요청 8회의 [기본 원본](../eval/results/critical_review_live_20261021.json), [대조 원본](../eval/results/critical_review_variants_20261021.json)입니다. 아래 시간·실패 사례는 **기존 실측**이며, 합격 기준은 **향후 목표**입니다. 현재 문제가 수정됐다는 뜻이 아닙니다.

| ID | 우선순위 | 문제 | 이번 개발의 완료 상태 |
|---|---|---|---|
| F1 | P1 필수 | 다른 프로젝트를 요청했는데 현재 프로젝트 조회 | 대상 불일치 시 도구 실행 전 차단·선택 안내 |
| F2 | P1 필수 | 실제 파일과 모순되는 설정 개선안 | 주장별 근거 검사, 미입증 주장 게시·승인 제외 |
| F3 | P1 필수 | 컨테이너 부재를 도구 실패로 처리 | 없음/중지/오류 구분, 의미 없는 재시도 종료 |
| F4 | P2 개선 | 교육 검색의 표현 의존성과 중복 확인 | 의미 기반 주제 연결, 확인된 정보 반영 |
| F5 | P2 개선 | 실행 종료·답변 검증·측정 지표 혼동 | 실행과 답변 상태 분리, route별 유효한 지표 |

이번 요청의 산출물은 이 기획안입니다. 구현·서버 재시작·Docker 조작은 수행하지 않습니다.

## 2. 유지할 원칙과 제외 범위

- **의도 분류는 계속 LLM 기반**입니다. 키워드 route fallback을 되살리지 않습니다. 코드의 대상·근거·권한 검증은 의도 분류와 별개입니다.
- 질문만으로 프로젝트를 자동 전환하지 않습니다. 기존 선택 패널에서 대상을 확인하고 전환합니다.
- 번호·자연어 확인 답변은 의도 확인이며 파일 변경·배포·재시작 승인이 아닙니다. 기존 2단계 승인·scope/hash 검증·롤백 경계를 유지합니다.
- 프로젝트 변경 시 대기 질문·미실행 승인 무효화, 대화 scope 분리, 실행 중 전환 차단을 유지합니다.
- 명확한 교육·파일 검토·서비스 상태 요청에 불필요한 질문이나 분석을 추가하지 않습니다.
- 첫 개선 범위는 로컬 1인·단일 백엔드 프로세스입니다. 다중 사용자·다중 worker·공개 API용 인증은 별도 개발 과제입니다.
- 프레임워크 이전, 임의 셸 도구, 자동 배포, 대형 벡터 DB, 새 Worker 추가, LangGraph 중간 checkpoint 재개는 이번 범위가 아닙니다.

## 3. F1 — 프로젝트 불일치 차단

### 3.1 현재 결함

현재 route는 허용 서비스명을 받지만 현재 프로젝트 식별자를 받지 않습니다. 따라서 skala-miniproject의 backend를 요청해도 bizxray의 backend라는 같은 서비스명으로 조회가 진행됩니다. 화면의 `X-Docker-Target` 검사는 오래된 클라이언트 연결을 막는 기능이지 자연어 요청의 대상 일치를 확인하는 기능이 아닙니다.

### 3.2 변경 설계

1. route 입력에 현재 엔진/context·프로젝트명·instance ID·허용 서비스를 전달합니다. 필요 시 발견된 프로젝트의 식별자/이름만 제한적으로 제공하며 다른 프로젝트 파일·로그를 미리 읽지 않습니다.
2. LLM 출력에 `requested_project`, `project_reference`(현재 대상/명시 대상/모호), `requested_service`를 구조화합니다. 사용자의 긍정 요청과 “보지 말라”는 제외 대상을 구분합니다.
3. **도구 실행 전 코드 검증**을 둡니다. 명시된 프로젝트가 현재 대상과 다르거나 확정할 수 없으면 파일·컨테이너 조회를 실행하지 않습니다. 프로젝트를 모델이 임의로 보정해도 허용하지 않습니다.
4. 프로젝트가 다른 경우에는 “현재 bizxray, 요청 skala-miniproject”를 보여주고 기존 프로젝트 선택 패널로 안내합니다. 이때 bizxray의 서비스 선택지를 질문하지 않습니다.
5. 프로젝트가 맞고 서비스만 빠졌을 때에만 기존 `human_question` 서비스 선택으로 보냅니다. 별칭·경로·동일 이름 등으로 대상이 모호하면 추측하지 않고 확인합니다.
6. 선택 패널에서 전환한 뒤 원래 요청을 다시 보낼 수 있는 버튼/보존 문구를 제공합니다. 전환과 요청 재실행은 분리하며 자동 실행하지 않습니다. 기존 대기 질문 토큰은 재사용하지 않습니다.
7. JSON 채팅, GET/POST SSE, slash 명령에도 같은 대상 검증을 적용합니다. 서비스명이 겹친다는 이유로 우회할 수 없어야 합니다.

예상 응답: “요청하신 프로젝트는 skala-miniproject지만 현재 연결 대상은 bizxray입니다. 아직 조회하지 않았습니다. 프로젝트 선택에서 대상을 바꾼 뒤 다시 요청해주세요.”

### 3.3 완료 기준

- 기존 skala-miniproject/backend 재현 문장에서 bizxray 관측 도구 **0회**.
- buttercast/api 요청에 ai/postgres/backend 선택지를 제시하지 않음.
- “현재 backend 상태”, “bizxray backend 상태”는 올바른 대상으로 직행하며 불필요한 프로젝트 질문 없음.
- “A 말고 B”, 알 수 없는 프로젝트, 모호한 별칭은 잘못된 조회 없이 명확하게 중단/확인.
- 오래된 instance ID, 전환 중 요청, 이전 승인·질문 재사용의 기존 차단 유지.

주요 변경 위치: `backend/routing.py`, `backend/graph.py`, `backend/server.py`, `backend/target_catalog.py`, `frontend/src/App.vue`, `frontend/src/components/TargetPanel.vue`. 프로젝트 확인을 선택지로 제공할 경우 `clarifications.py`의 질문 종류·허용 선택지도 함께 확장하며, 기존 서비스 allowlist를 프로젝트명으로 대체하지 않습니다.

## 4. F3 — 부재·중지·관측 실패 분리

F2보다 먼저 공통 관측 계약을 정리합니다. 이 계약이 설정 검토의 런타임 주장 검증에도 사용되기 때문입니다.

### 4.1 결과 계약

| 구분 | 의미 | 사용자 안내·그래프 처리 |
|---|---|---|
| 조회 성공 + 대상 존재 | 컨테이너 상태를 관측 | running/exited 등 실제 값 보고. health 값은 별도 표시 |
| 조회 성공 + 대상 부재 | 해당 scope의 완전한 목록에서 대응 컨테이너 없음 | “현재 대응 컨테이너 없음”으로 정상 종료. 재시도하지 않음 |
| 조회 성공 + 여러 대응 대상 | 단일 컨테이너로 확정 불가 | 개수·범위를 설명하고 필요한 경우에만 확인. 없음으로 바꾸지 않음 |
| 불완전한 목록/접근 실패 | 존재 여부 확정 불가 | “확인 불가”와 사유 표시. 부재나 중지로 단정 금지 |
| 일시적 통신 실패 | 재시도 가치가 있는 오류 | 도구 계층에서만 제한적 재시도. 그래프에서 동일 재시도를 중첩하지 않음 |
| 권한·인자·지원 범위 오류 | 같은 호출 반복으로 해결되지 않음 | 즉시 중단하고 해결 가능한 안내 |

`observation_status`(complete/partial/failed), `subject_status`(present/absent/ambiguous/unknown), lifecycle/health 값을 분리합니다. 성공적인 조회로 확인한 absent는 **유효한 근거**지만 정상 실행/healthy라는 뜻은 아닙니다.

### 4.2 변경 설계

1. `check_service_health`와 관련 도구에서 transport 성공 여부·부재 여부·실패 이유를 보존합니다. 내부 예외나 부분 결과를 단순 found=false로 바꾸지 않습니다.
2. `succeeded()`의 의미를 일괄 바꿔 모든 실패를 성공으로 간주하지 않습니다. “수집이 유효한가”와 “서비스가 정상인가”를 분리해 계획·진단·검증에서 일관되게 사용합니다.
3. 유효한 absent 결과에도 scope·관측 시각·근거 ID를 부여하고, Writer에서 일반 “관측 불가”로 축약하지 않습니다.
4. status 경로의 구조화된 정상/중지/부재 결과는 모델 재작성 없이 안전한 포맷으로 렌더링할 수 있게 합니다. 라우팅 LLM은 유지하며, 자명한 상태 보고에 추가 모델 호출을 강제하지 않습니다.
5. 재계획은 **새로운 근거를 얻을 수 있을 때만** 수행합니다. absent를 missing evidence로 세어 같은 도구를 세 번 호출하지 않습니다. 통신 재시도는 한 계층에서 최대 2회 추가로 제한하고 상한을 테스트합니다.
6. 최종 검증 실패 시 마지막 미검증 원고를 그대로 내보내지 않습니다. 확인된 관측·모르는 부분·미실행 사실만으로 구성한 안전한 결과를 반환합니다.

### 4.3 완료 기준

- 없는 ai/frontend 상태 요청: 논리적 상태 조회 1회, 불필요한 재계획·Writer 재시도 0회.
- 부재 응답이 “검증 미통과”가 아니라 근거 있는 유효 상태 보고로 종료.
- 중지 상태는 exited, healthcheck 미정의는 not_configured/해당 없음으로 표시. 둘을 unhealthy와 혼동하지 않음.
- Docker 연결 실패는 unknown/관측 실패이며 “컨테이너 없음”으로 보고하지 않음.
- 근거가 없는 [E1] 인용과 검증 실패 원고 노출 0건.

주요 변경 위치: `backend/docker_tools.py`, `backend/diagnostics.py`, `backend/planning.py`, `backend/agents.py`, `backend/graph.py`, 관련 MCP 출력·API 테스트.

## 5. F2 — 설정 검토의 주장별 사실 검증

### 5.1 현재 결함

실제 파일 읽기는 성공하지만, 검토 단계는 evidence ID의 존재만 검사합니다. 이미 적용된 npm ci·apt-get 결합을 다시 권하거나 Dockerfile/Compose만 보고 런타임 성공을 단정할 수 있습니다. 현재 configuration은 일반 Validator를 통과하지 않고 종료합니다.

### 5.2 검토 항목 계약

각 후보를 `파일 경로·hash / 줄 범위 / 실제 코드 조각 / 주장 / 종류 / 근거 ID / 예상 효과 / 확인이 필요한 사항`으로 구조화합니다. 종류는 관측 사실, 정적 위험, 런타임 주장으로 구분합니다. 인용 ID가 있다는 사실만으로 주장을 승인하지 않습니다.

검증 결과는 `supported / contradicted / insufficient`로 구분합니다. 확신 점수 하나로 내용을 통과시키지 않습니다.

### 5.3 변경 설계

1. 수집된 파일 snapshot에 줄 번호·hash·잘림 여부를 연결합니다. 검토 도중 파일이 바뀌거나 근거가 잘렸으면 완전한 파일인 것처럼 판단하지 않습니다. 비밀값 마스킹된 영역은 기존처럼 수정 근거에서 제외합니다.
2. Dockerfile별로 필요한 bounded 근거를 검토합니다. 필요 부분이 context 밖으로 잘린 경우에는 “확인 부족”을 명시하며 무리하게 수정안을 생성하지 않습니다. 모든 파일을 무제한 프롬프트에 넣지 않습니다.
3. 새 Worker 대신 기존 configuration 서브그래프에 `config_validate` 단계를 추가합니다. 검증 가능한 핵심 항목부터 코드 규칙으로 검사합니다.
   - 이미 `RUN npm ci`가 있으면 “npm ci로 바꾸라”는 권고 제외.
   - 다중 행 RUN을 포함해 apt update/install이 이미 결합됐으면 동일 결합 권고 제외.
   - healthcheck 선언·Compose 구문 유효성만으로 실행 성공/서비스 healthy 주장 금지.
   - 근거 없는 이미지 크기·빌드 시간 개선 수치 금지.
4. 위 규칙이 이해하지 못하는 복잡한 구문은 임의로 판정하지 않습니다. 파일 근거 대조와 기존 품질 모델의 제한된 2차 검토를 하되, 모델의 동의만으로 runtime 성공이나 성능 효과를 입증하지 않습니다.
5. contradicted 항목은 게시하지 않습니다. insufficient 항목은 “추가 확인 필요” 영역으로 분리하며 실행 권고나 승인 생성 근거로 사용하지 않습니다. 수정 가능한 사실관계 오류는 최대 한 번만 다시 검토하고, 다시 실패하면 확인된 사실만 게시합니다.
6. change 경로의 diff는 supported 항목과 정확한 파일 snippet/hash에 연결되어야 합니다. 기존 preview·파일 승인·배포 승인·롤백을 그대로 통과해야 하며, 검토 통과가 실행 승인을 대신하지 않습니다.
7. 구조/문법상 가능한 설정과 실제 동작 검증을 구분합니다. 실제 빌드·컨테이너 실행이 필요한 검증은 수행하지 않았다고 표시하고, 별도 승인 없이 실행하지 않습니다.
8. 검증 전 초안은 사용자용 확정 답변으로 보내지 않습니다. 기존 Writer처럼 토큰을 먼저 내보내고 나중에 경고만 붙이는 우회도 점검합니다. 검증이 필요한 답변 본문은 검증 후 공개하고, 대기 중에도 실제 노드 실행 이벤트는 계속 전달합니다. 디버그 입출력에 남긴 후보는 미검증 초안임을 명확히 표시합니다.

목표 경로: `config_collect → config_review → config_validate → config_propose`. 미검증 제안을 표시하는 현재 경고문만 강화하는 방식으로 완료 처리하지 않습니다.

### 5.4 완료 기준

- 기존 BE/FE 사례에서 이미 적용된 개선 권고 0건.
- 미배포 상태에서 healthcheck “작동 성공” 주장 0건.
- 게시되는 각 검토 항목에 실제 파일 위치·근거·검증 결과가 연결됨.
- findings를 모두 지워 오답을 없애는 방식도 불합격. 정답이 정의된 지원 항목에서는 필요한 문제를 찾아야 함.
- AI의 COPY→pip 설치 순서와 같은 캐시 후보는 실제 코드에 연결된 정적 위험으로 설명하며, 빌드 시간을 측정한 것처럼 말하지 않음. 패키징 구조 확인 없이 명령 순서를 자동 변경하지 않음.
- 모델/검증 실패 시에도 확인된 사실은 반환하고, 해당 결과로 변경 승인 생성 금지.

주요 변경 위치: `backend/config_agent.py`, `backend/project_files.py`, `backend/graph.py`, `backend/config_control.py`, `tests/test_config_control.py`. 필요 시 검증 함수만 작게 분리하고 일반 purpose 검증 프레임워크는 만들지 않습니다.

## 6. F4 — 교육 RAG 검색·질문 적합성 개선

### 6.1 변경 설계

1. 기존 5개 검토 카드는 유지합니다. 원문 키워드 검색은 후보 생성 수단으로 남겨도 되지만 검색의 전부로 사용하지 않습니다.
2. education으로 분류할 때 LLM이 질의를 짧은 학습 주제와 검색용 표현으로 정규화합니다. 예: “새 인스턴스로 교체 후 업로드 사진이 안 보임” → 데이터 영속성/컨테이너 수명. 가능하면 기존 route 호출의 구조화 출력에 포함해 별도 LLM 왕복을 늘리지 않습니다.
3. 정규화된 주제와 카드 제목·요약을 함께 사용해 후보를 고릅니다. 모델이 선택한 ID는 실제 카드 목록으로 검증하고, unrelated 카드를 억지로 반환하지 않습니다. 모호하거나 검색 실패하면 근거 부족을 안내합니다.
4. 답변을 `검토된 설명 원문 / 학습용 예시 / 아직 필요한 확인 질문`으로 분리합니다. 설명과 주의사항은 기존 검토 원문을 유지합니다.
5. 사용자가 명시한 사실만 구조화합니다. 삭제/재생성을 말했다면 그 여부를 다시 묻지 않습니다. 단, 삭제를 말했다고 마운트·백업 유무까지 추측하지 않습니다. 보존 예방법을 설명하는 데 필요하지 않은 실제 경로 입력을 강제하지 않습니다.
6. 교육적인 확인 질문은 `human_question` 작업 중단 질문과 구분합니다. 교육 답변 후 참고 질문을 제시하는 것만으로 작업을 대기 상태로 만들지 않습니다. 실제 환경 점검에 필수 인자가 없을 때만 중단 질문을 사용합니다.
7. 첫 단계는 새 벡터 DB·임베딩 모델 없이 시행합니다. 이후 동결된 독립 평가에서 검색 목표를 충족하지 못할 때만 로컬 임베딩 방식과 비교 평가하고, 의존성·모델 다운로드 비용을 별도 결정합니다.

## 7. F5 — 실행 상태·답변 품질·측정 지표 분리

### 7.1 사용자 표시

| 항목 | 예시 값 | 의미 |
|---|---|---|
| execution_status | running / waiting_for_user / completed / failed / cancelled | 실행이 어디까지 갔는가 |
| answer_status | validated / partial / unverified / unavailable | 답변이 어떤 근거·검증 수준인가 |
| subject_status | present / absent / ambiguous / unknown | 조회 대상의 존재를 확인했는가 |
| lifecycle / health | exited / running, healthy / unhealthy / not_configured / unknown | 컨테이너 존재와 별개의 런타임 상태 |

예: “실행 종료 · 대상 없음 · 근거 확인됨”, “실행 종료 · 파일 수집 완료 · 검토 미완료”, “답변 검증 실패 · 확인된 사실만 표시”. 검증되지 않은 원고를 일반 완료 답변과 동일하게 표시하지 않습니다.

브라우저의 스트림 닫기만 확인한 경우에는 ‘화면 수신 중단’으로 표시하고 서버 실행이 취소됐다고 단정하지 않습니다. `cancelled`는 서버가 실제 실행 취소를 확인한 경우에만 사용합니다.

### 7.2 지표 계약

- 미측정 값은 0이 아니라 null/해당 없음. 측정된 0과 구분합니다.
- 공통: 실제 모델 호출 수·도구 시도 수·고유 관측 수·실패 종류·경과 시간·대상 scope.
- configuration: 요청한 파일 범위 대비 수집 완전성, 검토/검증된 항목 수, 잘림·미지원 파일 수, 코드 검사 결과. 파일 수집률과 주장 정확도를 섞지 않습니다.
- status/incident: route별 필요한 관측의 충족 여부. 유효한 absent는 근거 충족이지만 healthy가 아닙니다.
- education: 검색 후보·최종 카드 ID·검색 방법·버전·출처 검증 결과. 교육에 장애 근거 coverage=0을 표시하지 않습니다.
- UI는 실제 NodeStarted/Completed를 계속 사용합니다. 상태 표시를 위해 가짜 노드나 예상 전체 노드를 추가하지 않습니다. 단순 상태 경로가 짧아지는 것은 정상입니다.
- 기존 응답 필드와 SSE 계약은 한 번에 제거하지 않습니다. 새 필드를 추가하고 프론트를 이행한 뒤, 의미가 바뀌는 필드는 README/API 버전과 테스트에 명시합니다.

완료 기준: configuration의 19회 관측을 미측정 tool_time_sum=0으로 표시하지 않고, 검증 미수행을 통과처럼 표시하지 않습니다. 상태·교육·설정·오류·취소·대기 각 화면을 브라우저에서 검증합니다.

## 9. 시험·평가지표·릴리스 게이트

### 9.1 평가 방법

- 기존 8회 재현 문장은 회귀용으로 보존합니다. 프롬프트 예시에 넣은 문장만으로 개선 효과를 주장하지 않습니다.
- 독립 평가: 5개 use case별 10개, 총 50개 문장을 기대값과 함께 동결합니다. 각 3회 반복하고 모든 결과를 기록합니다. 실패한 반복을 성공한 반복으로 덮어쓰지 않습니다.
- 결과 판정은 도구 인자·scope·관측 값·파일 snippet 및 사람이 검토한 정답을 기준으로 합니다. 같은 모델의 자기평가만으로 합격하지 않습니다.
- 모델 이름/가능한 버전 식별자, 설정, 실행 시각, 하드웨어, 모델 예열 여부, Docker 상태를 기록합니다. 먼저 순차 실행하고 동시 요청은 별도 부하 시험으로 분리합니다.
- 자동 테스트는 모델 대역을 사용한 계약/실패 주입과 실제 모델 평가를 구분합니다. 기존 233개는 회귀 점검 대상으로 유지하되, 의도적으로 바뀐 계약의 테스트는 변경 이유와 새 기대값을 명시합니다.
- 실제 Docker 기본 시험은 읽기 전용입니다. 정상 실행·OOM·통신 장애 재현이 필요하면 별도 일회용 Compose 스택·임시 폴더에서 수행하며 기존 bizxray를 변경하지 않습니다. 실제 스택 기동·승인 실행 시험은 구현 시 별도 범위 확인 후 진행합니다.

## 10. 위험·호환성 관리

- 관측 성공 판정을 바꾸면 원인 분류·근거 충족·승인 생성이 함께 달라질 수 있습니다. absent가 healthy/복구 가능으로 승격되지 않는 회귀 테스트를 우선 작성합니다.
- configuration 검증은 초기 지원 범위가 제한됩니다. 모르는 패턴을 정상이나 결함으로 단정하지 않고 확인 부족으로 남깁니다.
- 교육 질문을 별도 필드로 분리하면 원문 일치 테스트도 바뀝니다. 안전 경고·출처 검증을 유지하는 대체 검사를 먼저 정의합니다.
- 프로젝트명·로그·파일 내용은 모델에 대한 지시가 아닌 데이터입니다. 모델이 준 대상·경로·카드 ID는 서버의 allowlist·snapshot으로 검증합니다.
- 새 상태/질문 필드를 SQLite에 저장한다면 기존 pending 항목의 기본값·버전 처리를 정의합니다. scope/만료/한 번만 답변 가능 조건을 약화하지 않습니다. 불명확한 이전 항목은 안전하게 새 요청을 안내합니다.
- 승인 전 preview와 실제 파일 hash가 달라지면 기존처럼 재검토·재승인이 필요합니다. 이 개선은 권한 확대가 아닙니다.
- 단계별로 작게 반영하고 회귀가 나면 해당 코드 변경만 되돌립니다. 대화 DB 삭제·사용자 설정 초기화·Docker 볼륨 삭제를 복구 수단으로 사용하지 않습니다.

## 11. 완료 보고 형식

각 항목은 **완료 / 부분 완료 / 미완료**로 보고하고 다음을 첨부합니다.

1. 수정한 원인과 실제 변경 위치.
2. 이전 재현 문장의 전후 route·대상·도구·응답·검증 결과.
3. 독립 평가의 전체 시도/통과/실패와 원시 기록.
4. 안전 회귀·SSE/UI·production build 결과.
5. 미지원 구문, 남은 모델 오류, 실기 검증하지 않은 환경.

필수 수정 3개의 안전·정확성 게이트를 충족하기 전에는 “운영 판단을 맡길 수 있다”고 안내하지 않습니다. F4/F5까지 완료되고 같은 사용자 흐름을 다시 검증한 뒤 전체 개선을 완료 처리합니다.
