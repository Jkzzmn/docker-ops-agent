# 요청 의도와 실제 처리 불일치 수정 · 2026-10-22

이 문서는 10월 21일 흐름도 이후 추가된 실행 경로와 검토 정책을 설명합니다. 이전 PDF에는 `runtime_action` 노드가 없으므로 이 변경을 함께 확인해야 합니다.

## 보고된 원인

실제 SQLite 체크포인트에서 `api 상태만`은 status, Dockerfile 비효율 질문은 configuration, `도커 띄워줘`는 change로 분류된 것을 확인했습니다. 마지막 요청은 시작 기능이 아닌 파일 검토로 흘렀습니다. Dockerfile은 읽었지만, 좁은 정적 규칙과 공통 답변 템플릿 때문에 질문에 필요한 코드 설명이 빠졌습니다.

## 변경된 경로

```text
상태만 요청 → route → status_observe → 한국어 실행 상태와 health 한계 → END
Dockerfile 검토 → route → configuration
  → config_collect: 실제 파일·컨테이너 수집
  → config_review: 질문에 맞는 파일로 문맥을 좁혀 QUALITY 모델이 줄 번호 기반 검토
  → config_validate: 코드 규칙 + 원본 줄 인용 + 독립 의미 검증
  → config_propose: 관측 사실 / 정적 위험 / 검토 의견을 구분 → END
시작·중지·재시작 → route(runtime + operation + 원문 action_quote)
  → runtime_action: 현재 대상·기존 컨테이너·정확한 명령을 미리보기
  → 이미 목표 상태면 변경 없이 종료, 아니면 1회 승인 생성 → END
  → 별도 승인 API → execute_runtime_action → 실제 실행 상태 재조회
```

자연어 의도는 LLM이 분류합니다. runtime의 operation과 원문 인용은 구조화 스키마의 필수 필드이며, 코드가 허용 작업·서비스·대상 출처를 검사합니다. 작은 모델의 누락을 줄이도록 기존 라우터 프롬프트도 간결하게 정리했습니다. 라우팅 실패를 키워드 교육 답변으로 바꾸지는 않습니다.

## 실행 지원 범위와 안전 경계

- 현재 선택한 Compose 프로젝트의 **기존 컨테이너**에 대한 start/stop/restart만 지원합니다.
- 기본 명령은 `docker compose start|stop|restart <표시된 서비스>`이며 임의 shell 문자열을 받지 않습니다.
- 프로젝트 전체라는 요청은 허용 서비스 전체, 명시한 단일 서비스는 그 서비스만 대상으로 합니다. 대상이 모호하면 기존 확인 질문 경로를 사용합니다.
- 미리보기는 변경하지 않습니다. 이미 요청한 상태라면 불필요한 승인을 만들지 않습니다.
- 실제 실행에는 서명·만료·범위가 일치하는 승인 하나가 필요합니다. 승인 직전에 Engine/context, Compose와 관련 파일 hash, 컨테이너 ID·이미지·실행 상태를 다시 대조합니다.
- 승인 소비 뒤 timeout이 나면 결과가 불확실하므로 자동 재시도하지 않습니다. MCP도 이 변경 도구는 1회만 시도합니다.
- 새 컨테이너 생성, 이미지 pull/build, Docker Desktop/Engine 자체의 기동은 이 경로의 지원 범위가 아닙니다. 해당 경우 지원 한계를 직접 안내하며 파일 검토로 대체하지 않습니다.
- start는 기존 컨테이너의 이미지·설정을 사용합니다. Dockerfile을 바꿨다고 자동 재빌드하지 않습니다.
- 사후 running/exited 확인과 애플리케이션 readiness는 다릅니다. healthcheck가 없으면 정상·준비 완료를 확정하지 않습니다.

## Dockerfile 검토 개선

Dockerfile만 물었으면 최종 답변을 Compose healthcheck 공통 문구로 채우지 않습니다. 실제 수집한 Dockerfile의 줄 수와 확인 가능한 코드 순서, 파일 위치를 보여줍니다. 이미 의존성 파일 COPY → pip 설치 → 나머지 파일 COPY 순서로 분리돼 있으면 그 사실을 코드로 확인해 모델에 제공하고, 무조건 순서를 바꾸라는 잘못된 조언을 줄입니다.

기존 코드 규칙으로 입증되는 정적 위험은 그대로 게시합니다. 그 밖의 모델 의견은 실제로 수집한 파일의 정확한 줄·고유 코드 조각과 해당 evidence ID에 연결되어야 하며, 독립 모델이 현재 질문과 기술적 맥락을 대조한 뒤에만 별도 검토 의견으로 표시합니다. 모델이 임의의 코드나 인용을 만들거나 검증 모델이 실패하면 게시하지 않습니다. 모델 판단 자체가 무오류라는 의미는 아닙니다.

확인된 사실을 다시 설명한 의견을 개선점으로 세지 않도록 `review_comments`와 `review_suggestions`를 구분했습니다. 의견이 있다는 이유로 성능 저하나 개선 효과가 실측됐다고 표시하지 않습니다. 임의의 새 규칙을 모델 의견으로 가장해 파일 수정 권한을 얻을 수도 없습니다. 자동 파일 diff는 기존의 관측상 누락된 .dockerignore 추가 범위를 유지합니다.

추가 모델 호출이 필요한 기술 검토는 QUALITY를 사용하며, 라우팅과 짧은 일반 응답은 기존 경량 역할을 유지합니다. 별도 무한 재작성 루프는 추가하지 않았고 요청 예산 60초·모델 8회·도구 24회도 유지합니다.

## 요청-결과 계약

공통 JSON/SSE 실행기는 runtime 요청에 configuration 답변이 붙는 것처럼 결과 종류가 어긋나면 승인·제안을 제거하고 요청에 맞는 결과를 만들지 못했다고 명시합니다. 이 검사는 의도 모델이 항상 맞다는 보장이 아니라, 이미 분류된 경로와 실제 결과가 다시 뒤섞이지 않게 하는 코드 계약입니다.

## 검증

`tests/test_intent_fulfillment.py`는 시작·중지·재시작 승인, 기존 컨테이너만 허용, 설정·identity 변경 시 차단, 승인 재사용·timeout 재시도 차단, 파일 인용의 정확성, 독립 검증의 수락/거절, 기존 의존성 순서 확인, 요청-결과 불일치 차단을 확인합니다. 실제 변경 명령은 테스트 double로 검증해 사용자의 buttercast를 임의로 시작하지 않습니다.

`eval/intent_fulfillment_live.py`는 보고된 세 질문을 실제 Ollama와 현재 buttercast 읽기 도구로 순서대로 실행합니다. runtime은 승인 생성까지만 확인하고 그 테스트 승인을 거절합니다. 파일에 실제로 없는 개선점을 만들어야 통과하는 평가가 아니라, 질문에 맞는 파일·코드 설명이 있는지 확인합니다. 원시 결과는 `eval/results/intent-fix-*.jsonl`이며 실패한 중간 기록도 남깁니다. 각 실행 1회는 모든 자연어 정확도를 보장하지 않습니다.

이번 변경은 로컬 앱에 반영하며 GitHub에는 추가 push하지 않습니다.

### 최종 확인 기록

브라우저 SSE 경로도 `도커 띄워줘`로 확인했습니다. 실제 실행 단계는 route와 runtime_action 두 개이며, `docker compose start api worker`와 **승인하고 시작** 버튼이 표시됩니다. 검증용 승인은 거절했고 화면에서 **아무것도 변경하지 않았습니다**를 확인했습니다. 증거 화면은 `output/ui/runtime-start-approval.jpg`, `output/ui/runtime-start-rejected.jpg`입니다. 서버 재시작 전의 개발 화면이 이전 JavaScript를 유지해 처음에는 옛 재시작 버튼이 표시됐으나, 새로고침 뒤 최신 UI로 확인했습니다. 기존 Vite HMR 연결 오류 로그와 기능 실행 오류는 구분해야 합니다. 최종 UI 변경 후 프론트 10개 테스트와 production build도 다시 통과했습니다.
