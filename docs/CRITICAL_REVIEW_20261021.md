## 종합 판단

이 서비스는 Docker 교육과 프로젝트 파일/컨테이너 관측을 연결하는 로컬 에이전트입니다. 현재 로컬 1인·단일 백엔드 프로세스 사용을 전제로 평가했습니다. **파일을 실제로 읽고 안전 경계를 지키는 기반은 있지만, 사용자가 믿고 운영 판단을 맡길 정확성은 아직 부족합니다.** 특히 프로젝트 불일치 차단과 설정 검토의 사실 검증을 먼저 보완해야 합니다.

핵심 유스케이스 5개와 표현 변형·후속 답변을 포함해 실제 앱 요청 8회를 실행했습니다. 다음 결과는 의도적으로 고른 소규모 실패 탐색 사례이며 전체 정확도/성공률 추정이 아닙니다. 이번 평가에서 수정·배포·재시작 승인을 실행하거나 진단 대상을 전환하지 않았습니다. 대화·확인 질문 및 평가 결과 기록만 남았습니다.

- 대조 실험 원본: [critical_review_variants_20261021.json](../eval/results/critical_review_variants_20261021.json)

## 반드시 고칠 결점

### 1. [P1] 질문에 명시된 프로젝트와 실제 조회 프로젝트가 다름

- **역할:** 라우터는 자연어 요청을 도구 인자로 바꾸며, MCP는 화면에서 선택된 프로젝트에 고정됩니다.
- **재현·문제:** skala-miniproject/backend를 명시하고 bizxray 조회를 금지했는데, 응답 metadata.docker_target.project=bizxray 상태로 backend check_service_health를 3회 호출했습니다. 초기 목록에서 skala-miniproject/backend는 실제 존재했지만, 앱은 bizxray에서 찾지 못한 결과를 보고했습니다. 단순 말투 문제가 아니라 관측 대상 자체가 틀렸습니다.
- **최소 수정 방향:** 현재 프로젝트 식별자를 라우터 입력에 포함하고, 요청의 프로젝트를 구조화된 필드로 받습니다. 요청 대상과 연결 대상이 다르면 도구 실행 전에 멈추고 프로젝트 선택 패널을 안내해야 합니다. 자동 전환/추측으로 해결하지 않습니다.
- **방치하면:** 같은 서비스명을 쓰는 여러 프로젝트에서 잘못된 장애 판단을 합니다. 현재 실험에서 변경 실행은 없었지만 변경 제안으로 이어질 경우 더 위험합니다.

근거 코드: [graph.py:104](../backend/graph.py#L104)는 available_services만 전달하며 프로젝트 식별자는 전달하지 않습니다. [routing.py:94](../backend/routing.py#L94)는 서비스 allowlist와 서비스명 출처만 확인하고, [planning.py:60](../backend/planning.py#L60)은 scope/service만 계획에 사용합니다. X-Docker-Target은 화면의 연결이 오래됐는지 검증할 뿐 자연어의 프로젝트 불일치는 잡지 못합니다.

### 2. [P1] 설정 검토가 실제 파일과 모순되는 조언을 인용과 함께 게시

- **역할:** configuration은 실제 파일을 읽어 오류·비효율을 설명합니다.
- **재현·문제:** E9의 BE Dockerfile에는 이미 `RUN apt-get update`와 `&& apt-get install`이 한 RUN으로 있습니다. 그런데 결합하라는 개선안을 냈습니다. E11의 FE는 이미 `RUN npm ci`인데 npm ci 사용을 다시 권했습니다. 또한 실행 컨테이너가 없는 AI healthcheck를 “성공적으로 작동”한다고 썼습니다.
- **최소 수정 방향:** 검토 항목마다 현재 코드 조각·문제 주장·기대 효과를 연결하고, 실제 파일과 모순되거나 이미 적용된 권고는 제거합니다. configuration에도 독립 근거 검증을 적용하되, 다른 LLM의 동의만으로 통과시키지 말고 명백한 사실은 코드 검사로 제한해야 합니다. 정적 유효성과 런타임 성공을 별도 상태로 표시해야 합니다.
- **방치하면:** 초보 사용자가 정상 설정을 문제로 오해하고 불필요하거나 잘못된 수정을 하게 됩니다. ‘미검증 가설’이라는 경고는 투명성에는 도움이 되지만 잘못된 조언을 유용한 결과로 바꾸지는 못합니다.

근거 코드: [config_agent.py:97](../backend/config_agent.py#L97)는 evidence ID가 존재하는지만 필터링합니다. 주장과 내용의 일치는 검사하지 않으며, [config_agent.py:149](../backend/config_agent.py#L149)는 review→propose→END로 종료합니다. 이번 기록의 validation_attempts=0, validation_ok=null입니다.

검토가 놓친 구체적 후보도 있습니다. AI Dockerfile은 `COPY app`/`COPY eval` 뒤에 `RUN pip install '.[parsing,models]'`이 있어 앱 코드 변경이 무거운 설치 레이어 캐시를 무효화할 수 있습니다. 이는 파일과 [Docker 공식 캐시 무효화 규칙](https://docs.docker.com/build/cache/invalidation/)을 대조한 **추론**이며 빌드 성능을 측정한 결론은 아닙니다. 패키징 구조 확인 없이 단순 명령 순서 변경을 바로 적용해서도 안 됩니다.

### 3. [P1] ‘컨테이너 없음’을 정상 관측 결과로 표현할 수 없어 불필요한 재시도·검증 실패 발생

- **역할:** 상태 조회는 실행·중지·미배포를 간단하게 구분해야 합니다.
- **재현·문제:** ai 조회에서 `{ok:false, found:false}`가 3회 반복됐습니다. Writer에는 found=false가 아닌 일반 ‘관측 불가’ 사유만 전달되고, 검증기는 유효한 E 인용을 반드시 요구합니다. 성공 근거 ID 집합이 비어 있으므로 올바른 ‘관측하지 못함’ 답변조차 이 경로로는 합격할 수 없습니다. 최종 답변은 검증 실패 경고와 부적절한 [E1] 인용을 그대로 내보냈습니다. frontend 확인 답변에서도 같은 구조가 재현됐습니다.
- **최소 수정 방향:** 조회 성공과 대상 부재를 분리한 결과 타입을 사용합니다. 완전한 프로젝트 목록에서 확인한 not_found는 유효한 관측으로 보고 한 번에 종료하고, 통신 실패 등 재시도 가능한 오류만 다시 시도해야 합니다. 알 수 없음은 ‘없음’과 구분해야 합니다. 검증 실패 시 마지막 잘못된 원고 대신 확정 가능한 구조화된 결과를 보여줘야 합니다.
- **방치하면:** 가장 흔한 ‘아직 안 띄운 서비스’가 장애처럼 보이고 사용자는 10~18초를 기다린 뒤 실패 안내를 받습니다.

근거 코드: [docker_tools.py:180](../backend/docker_tools.py#L180), [agents.py:24](../backend/agents.py#L24), [agents.py:52](../backend/agents.py#L52), [agents.py:279](../backend/agents.py#L279), [graph.py:265](../backend/graph.py#L265).

## 다음으로 고칠 결점

### 4. [P2] 교육 RAG가 표현 변화에 취약하고 이미 준 정보를 다시 질문

- **역할:** 초보자의 증상을 검토된 교육 근거에 연결합니다.
- **재현·문제:** ‘컨테이너 삭제·저장·사라짐’은 K1/K2를 찾지만 ‘새 인스턴스·업로드 사진이 보이지 않음’은 education으로 정확히 분류하고도 0건을 반환했습니다. 지식이 없는 것이 아니라 연결에 실패한 것입니다. 성공 사례도 이미 삭제·재생성을 말했다는 점을 반영하지 않고 “중지만 했나요, 삭제하고 새로 만들었나요?”를 다시 출력했습니다.
- **최소 수정 방향:** 검색 전 의미에 맞는 질의 정규화·동의어 확장을 하고 관련성이 확실한 카드만 제시합니다. 답변 원문을 안전하게 유지하더라도 이미 답한 질문은 생략하고, 사용자에게 남아 있는 확인 항목을 따로 표시해야 합니다. 카드 수가 5개인 현재 단계에서는 대형 벡터 DB부터 도입할 필요는 없습니다.
- **방치하면:** 사용자가 정확한 키워드를 알아야만 교육을 받을 수 있습니다. 이는 초보자를 위한 자연어 도우미라는 목적과 어긋납니다.

근거 코드: [knowledge.py:13](../backend/knowledge.py#L13)는 키워드 일치 수로 상위 3개를 반환합니다. [agents.py:225](../backend/agents.py#L225)와 [knowledge.py:23](../backend/knowledge.py#L23)는 안전 카드 원문을 그대로 조합합니다. 교육 내용의 컨테이너 삭제/볼륨 수명 설명은 [Docker 공식 문서](https://docs.docker.com/engine/storage/volumes/)와 대조해 타당했습니다. 문제는 그 원문이 아니라 검색·개인화입니다.

### 5. [P2] 화면·평가 지표가 ‘실행 종료’와 ‘유효한 답변’을 분리하지 못함

- **역할:** 실행 그래프와 지표는 사용자가 무엇을 믿을 수 있는지 알려줘야 합니다.
- **재현·문제:** 설정 검토는 근거 19개를 읽었지만 metadata에서 evidence_coverage=0, evidence_sufficient=false, agents_run=[], tool_time_sum=0입니다. 이 경로에서 지표가 계산되지 않았기 때문입니다. UI 코드도 metadata만 있으면 validation_ok=false인 응답을 ‘완료’로 표시합니다. 별도 경고문은 있으나 완료/성공/미검증을 일관되게 구별하지 못합니다. UI 표시는 이번에 브라우저 재실험한 결과가 아니라 실제 응답과 렌더링 코드를 대조한 결과입니다.
- **최소 수정 방향:** execution_status와 answer_status를 분리하고, 미측정 지표는 0 대신 null/해당 없음으로 표시합니다. 각 route의 커버리지와 검증 기준을 정의한 뒤 측정해야 합니다. 실패·미검증 원고는 완료된 진단과 시각적으로 구별해야 합니다.
- **방치하면:** 노드가 많이 실행됐다는 것이 정확한 진단의 증거처럼 보이고, 평가 지표도 개선 효과를 제대로 비교하지 못합니다.

근거 코드: [server.py:183](../backend/server.py#L183)는 진단 경로의 기본값을 configuration에도 사용합니다. [App.vue:64](../frontend/src/App.vue#L64)는 metadata 존재 여부로 완료를 정합니다. [config_agent.py:62](../backend/config_agent.py#L62)는 전체 파일 관측 경로지만 일반 Worker 보고/커버리지 계산과 연결되지 않습니다.

## 잘된 점과 평가 해석

- 명확한 파일 검토는 configuration으로 분류됐고 실제 선택 프로젝트의 파일을 읽었습니다. 예전처럼 교육 카드로 대체되지는 않았습니다.
- 모호한 서비스 요청은 도구 0회로 질문했고, 목록에 없는 네 번째 서비스 frontend를 자연어로 확정한 뒤 해당 서비스만 조회했습니다.
- 교육 원문은 출처를 제시하고 ‘볼륨 추가가 이미 지워진 데이터를 되살리지는 않는다’, ‘볼륨은 백업이 아니다’라는 안전 맥락을 유지했습니다.
- 이번 8개 요청에서는 승인 객체나 변경 작업을 실행하지 않았습니다. 단, 이는 모든 악성 입력·권한 경계에 대한 침투 테스트를 통과했다는 뜻은 아닙니다.
- 기존 자동 테스트 233개 통과는 절차·계약·안전 경계의 근거이지 답변 정확도 100%의 근거가 아닙니다. 예를 들어 [test_config_control.py:245](../tests/test_config_control.py#L245)는 정해진 모델 응답으로 route·노드·승인·파일 불변을 검증하며 실제 모델 권고의 참/거짓을 평가하지 않습니다.

## 다음 평가의 합격 기준

1. **대상 일치:** 명시된 프로젝트/서비스와 실제 관측 scope가 일치하거나, 도구 0회로 선택을 요청해야 합니다. 프로젝트 충돌 시 잘못된 조회는 0건이어야 합니다.
2. **사실 정확성:** 각 주장마다 파일 줄/관측 값으로 참·거짓·미확인을 평가합니다. 이미 적용된 개선안, 미관측 런타임 성공 주장을 허용하지 않습니다.
3. **부재 처리:** 미배포·통신 실패·health 미정의를 분리합니다. not_found를 불필요하게 반복 조회하지 않고 유효한 결과로 종료해야 합니다.
4. **질문 적합성:** 반드시 필요한 경우만 질문하며, 사용자가 이미 제공한 정보를 다시 요구하지 않습니다. 답변 후 의도/대상/승인 경계를 따로 평가합니다.
5. **검색 재현율·답변 유용성:** 같은 의미의 다양한 초보자 표현으로 같은 관련 근거를 찾는지 평가합니다. 미검색을 안전하게 인정하는 것과 지식을 잘 찾는 것은 별개 지표입니다.
6. **지연·호출 효율:** 성공과 실패를 나누어 응답 시간·모델/도구 호출을 측정합니다. 노드 수 자체를 성능 점수로 사용하지 않습니다.

순서는 **프로젝트 불일치 차단 → 설정 주장 검증 → 부재 상태/실패 모델 정리 → 검색 표현 확장 → 지표 정합성**을 권합니다. 현 단계에서는 에이전트 수나 그래프 노드를 더 늘리기보다 이 경계들을 명확히 하는 것이 중요합니다.

## 한계·미검증

현재 중지/미배포 환경만 사용했습니다. 정상 실행·OOM·실제 네트워크 장애를 새로 만들지 않았고, 파일 적용/빌드/롤백/승인 실행, OpenAI backend, Windows·원격 엔진, 다중 사용자·부하·침투 테스트는 이번에 수행하지 않았습니다. 전체 저장소의 모든 줄을 읽은 보안 감사가 아니라 위 5개 사용자 흐름과 관련 경로를 깊게 본 평가입니다. 기존 graphify 그래프가 없어 소스와 실제 노드 trace를 직접 대조했습니다. 구현은 수정하지 않았고 보고서/실험 원본만 추가했습니다.
